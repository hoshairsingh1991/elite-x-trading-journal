# ELITE X TRADING JOURNAL — PERFORMANCE BREAKDOWN MASTER NOTES

## 1. MODULE PURPOSE

Performance Breakdown provides detailed trading performance analysis across three views:

1. Mix — asset classes and trade directions.
2. Weekday — performance by day of the week.
3. Symbol — performance by individual ticker.

Each view supports four metrics:

- Trades
- Net P&L
- Win Rate
- Commissions

The purpose is to help traders identify which asset classes, directions, weekdays, and individual symbols contribute positively or negatively to trading performance.

This module uses the canonical trade records and existing analytics pipeline. It must not independently reconstruct trades or implement a separate accounting system.

## 3. CANONICAL DATA FLOW

The main data flow is:

Canonical executions
    ↓
FIFO trade reconstruction
    ↓
Canonical Trade records
    ↓
Dashboard account filtering
    ↓
Dashboard date filtering
    ↓
FX conversion into the selected reporting currency
    ↓
generatePerformanceBreakdownAnalytics(reportingTrades)
    ↓
PerformanceBreakdownData
    ↓
Mix / Weekday / Symbol aggregation
    ↓
Performance Breakdown metric calculations

The Performance Breakdown analytics function receives the already-filtered and converted trades.

The component must not:
- Reconstruct executions into trades.
- Apply FIFO matching.
- Independently convert the same P&L values again.
- Reapply the dashboard date filter.
- Reapply the dashboard account filter.
- Add a second, independent accounting pipeline.

The canonical dashboard data is the source of truth.

## 4. ACCOUNT FILTERING AND DATE FILTERING

In `app/dashboard/page.tsx`, the dashboard first builds `accountFilteredTrades`.

When `selectedAccount === "ALL"`:
- All imported trades are eligible for the selected date range.

Otherwise:
- Only trades whose `trade.account` matches `selectedAccount` are included.

The dashboard subsequently creates `filteredTrades` using the selected date range.

The date filter:
- Includes trades on the selected start date.
- Includes trades on the selected end date.
- Uses the trade's `date` field.
- Constructs date boundaries using local JavaScript Date objects.

If either `startDate` or `endDate` is missing, the date filter currently allows the trades through without applying a date restriction.

For the YTD preset, the date range is initialized and generated from January 1 of the current year through the current day.

All Performance Breakdown calculations operate on the resulting filtered dataset, after currency conversion.

When investigating a discrepancy, always verify:
1. Selected account.
2. Selected date range.
3. Number of filtered trades.
4. Reporting currency.
5. Completed versus open trade counts.

A difference in any of these may explain discrepancies between different dashboard sections.

## 5. REPORTING CURRENCY AND FX CONVERSION

### Reporting currency selection

The dashboard stores the selected reporting currency in the `reportingCurrency` state.

The default is USD.

The selected currency is persisted using the local storage key:

`reportingCurrency`

Supported currencies in the current FX rate model:
- USD
- CAD
- EUR
- GBP
- JPY
- INR

### Conversion pipeline

The dashboard executes the equivalent of:

`convertTradesToReportingCurrency(filteredTrades, reportingCurrency, fxRates)`

The resulting array is called `reportingTrades`.

Performance Breakdown analytics is generated from:

`generatePerformanceBreakdownAnalytics(reportingTrades)`

Therefore:
- P&L values supplied to Performance Breakdown are intended to be in the selected reporting currency.
- Fees supplied to Performance Breakdown are intended to be in the selected reporting currency.
- Trade History may continue to show each trade in its original currency.

Do not compare a direct sum of mixed-currency Trade History P&L against the dashboard's reporting-currency total without converting the amounts first.

### FX conversion formula

The conversion function first checks whether the source and target currencies match.

If they match, the original amount is returned.

Otherwise:

USD amount = Original amount × Source currency rate

Target amount = USD amount ÷ Target currency rate

The FX rate convention is:

`1 unit of a currency = its value in USD`

USD has a normalized rate of `1`.

For example, if CAD is `0.73` and USD is `1`:

CAD 100 × 0.73 = USD 73

This is an illustrative example, not a guaranteed live exchange rate.

### Live rates

The live API currently requests USD-based rates from Frankfurter and inverts the foreign-currency rates.

For example:

`CAD = 1 / data.rates.CAD`

This normalization is consistent with the conversion function's expected rate convention.

### Cache and fallback behavior

The current FX provider:
- Caches rates in local storage.
- Uses a 12-hour cache duration.
- Attempts to fetch live rates when the cache is missing or expired.
- Falls back to cached rates if fetching fails.
- Uses static fallback rates if neither live nor cached rates are available.

Current static fallback rates:

- USD: 1
- CAD: 0.73
- EUR: 1.14
- GBP: 1.34
- JPY: 0.0068
- INR: 0.012

These are fallback values, not authoritative current rates.

### Important FX risks

The current conversion function returns the original amount if it cannot find a source or target currency rate.

This means an unsupported or missing rate can allow an amount to pass through without the required conversion.

This behavior should be reviewed in a future FX-hardening task. Any change should include explicit handling and tests rather than silently changing the existing conversion contract.

Another important detail:

`convertTradesToReportingCurrency` changes `trade.pnl` and `trade.fees` but preserves the original `trade.currency` and `trade.feeCurrency` values.

Consequently, the converted monetary values may coexist with currency metadata that still represents the trade's original currency.

Do not assume that `trade.currency` inside `reportingTrades` has been rewritten to the selected reporting currency. Any future downstream calculation must understand this distinction and must not accidentally reconvert values.

## 6. COMPLETED TRADE RULE

The analytics module uses the following completion rule:

`!trade.isOpen && trade.status !== "OPEN"`

A trade is considered completed when:
- `isOpen` is false.
- `status` is not `"OPEN"`.

Open trades are excluded from completed-trade P&L and Win Rate calculations.

This rule is used consistently by the module's completed-trade helper.

Important:
A record with `isOpen === false` and a status other than `"OPEN"` is treated as completed under the current implementation.

Do not casually change this rule without inspecting all supported trade sources and lifecycle states.

## 7. MIX VIEW — CATEGORY CLASSIFICATION

The Mix view categorizes trades based on asset type, option type, manual-trade detection, and trade direction.

### Asset type normalization

The analytics normalizes these values:

Stocks:
- STOCK
- STOCKS
- STK

Options:
- OPTION
- OPTIONS
- OPT

Crypto:
- CRYPTO

Forex:
- FOREX
- CASH

Futures:
- FUT
- FUTURE
- FUTURES

Anything not recognized falls into Other.

### Standard Mix categories

Stocks:
- Left: LONG
- Right: SHORT

Options:
- Left: CALLS
- Right: PUTS

Crypto:
- Left: LONG
- Right: SHORT

Forex:
- Left: LONG
- Right: SHORT

Futures:
- Left: LONG
- Right: SHORT

### Manual options

Manual trades are detected when:
- `contractKey` is missing or empty after trimming, or
- `contractKey` starts with `MANUAL-`.

Manual option trades are placed in the `manual-options` group.

Their direction is based on `trade.side`:
- LONG goes to the left.
- SHORT goes to the right.

The group is labelled `Man. Opt.`

### Option type detection

The analytics examines both `contractKey` and `contract`.

It supports contract representations such as:
- `QQQ_2026-05-15_C_480`
- `QQQ_2026-05-15_P_510`
- `QQQ_2026-05-15_C`
- `QQQ 15 MAY 2026 480 CALL`
- `SPY 15 MAY 2026 510 PUT`

The regular expressions identify CALL and PUT tokens.

When a non-manual option cannot be classified unambiguously:
- It is placed in `unclassified-options`.
- It is not guessed to be a CALL or PUT.
- The displayed group is `Opt. Other`.
- Its left/right direction follows LONG/SHORT.

### Conditional categories

The following rows are included only when they contain at least one trade:
- Other
- Man. Opt.
- Opt. Other

The standard categories remain available even when they contain zero trades:
- Stocks
- Options
- Crypto
- Forex
- Futures

Mix rows are sorted by the combined left and right trade counts, descending.

The current row counts include open trades.

## 8. MIX VIEW — METRIC CALCULATIONS

Each Mix row calculates left and right metrics independently.

### Trades

`leftTrades = bucket.left.length`

`rightTrades = bucket.right.length`

These counts include both completed and open trade records.

Consequently, the count displayed in a Mix row may be greater than the number of trades used to calculate its Net P&L or Win Rate.

The current analytics model also exposes:

- `leftCompletedTrades`
- `rightCompletedTrades`

These count completed records only. They should be reused if a future change needs completed-trade counts rather than independently rebuilding the count logic.

### Net P&L

Net P&L is the sum of `trade.pnl` for completed trades only.

Open trades are excluded.

The function sums the P&L stored on each completed canonical Trade record. It does not independently reconstruct entry/exit executions.

For the canonical FIFO-generated trades, the trade P&L is already calculated by the trade reconstruction layer.

The analytics must not subtract fees again unless the underlying canonical P&L definition changes. Doing so could double-count fees.

### Win Rate

Win Rate is calculated using completed trades only.

Formula:

Win Rate = Winning Completed Trades ÷ Total Completed Trades × 100

A winning trade is a completed trade whose status is exactly `"WIN"`.

The result is rounded to one decimal place.

If there are no completed trades, the function returns `0`.

A losing trade cannot make Win Rate negative.

Examples:
- 0 winners out of 1 completed trade = 0%.
- 5 winners out of 10 completed trades = 50%.
- 10 winners out of 10 completed trades = 100%.

Under the current function, a completed breakeven trade is included in the denominator but is not classified as a win.

### Commissions

Mix commissions sum `trade.fees` across all records in the relevant bucket, including open and completed trades.

The fees have already passed through the reporting-currency conversion pipeline.

This differs from Net P&L and Win Rate, which exclude open trades.

## 9. WEEKDAY VIEW — AGGREGATION

The Weekday view groups completed trades by their `trade.date`.

For reconstructed completed trades, the canonical trade date is the closing date.

This means Weekday performance is attributed to the day the trade closed, not necessarily the day it was opened.

### Local date parsing

The analytics parses the date portion of `trade.date`.

It expects a valid `YYYY-MM-DD` date.

It constructs a local JavaScript Date and rejects invalid calendar dates.

Records with invalid dates are skipped in the weekday aggregation.

### Displayed weekdays

Monday through Friday are always included.

Saturday is included only when at least one completed trade falls on Saturday.

Sunday is included only when at least one completed trade falls on Sunday.

### Weekday trade counts

Weekday counts use completed trades only.

Open positions do not contribute to weekday trade counts.

This differs from the Mix and Symbol views.

### Weekday Net P&L

Weekday P&L sums completed-trade P&L for that weekday.

Open-trade P&L is excluded.

### Weekday Win Rate

Weekday Win Rate uses completed trades attributed to that weekday.

The formula remains:

Winning Completed Trades ÷ Total Completed Trades × 100

The result is rounded to one decimal place.

If there are no completed trades for a weekday, the returned Win Rate is `0`.

### Weekday commissions

Weekday aggregation first filters the dataset to completed trades.

Consequently, Weekday commissions also sum fees from completed trades only.

This differs from Mix and Symbol, where commission totals include open trades.

This difference is part of the current implementation and must be considered when comparing views.

## 10. SYMBOL VIEW — AGGREGATION

The Symbol view groups trades by normalized ticker.

The symbol normalization:
- Trims whitespace.
- Converts tickers to uppercase.
- Uses `UNKNOWN` if the ticker is empty.

### Symbol trade count

Symbol trade count includes every record grouped under the ticker, including open trades.

### Symbol asset label

The analytics collects the distinct normalized asset types represented by trades for that ticker.

If there is one asset type, that asset is displayed.

If the ticker contains multiple asset types, the asset is labelled `Mixed`.

### Symbol Net P&L

Symbol P&L sums completed-trade P&L only.

Open-trade P&L is excluded.

### Symbol Win Rate

Symbol Win Rate uses completed trades only.

The winning-trade condition is exactly:

`trade.status === "WIN"`

The result is rounded to one decimal place.

If there are no completed trades for the ticker, Win Rate is `0`.

### Symbol commissions

Symbol commissions sum `trade.fees` from every trade record grouped under the ticker, including open trades.

The amount is already intended to be in the reporting currency because the records enter Performance Breakdown after the FX conversion step.

### Symbol ordering

Rows are sorted by:
1. Trade count descending.
2. Symbol alphabetically when trade counts are equal.

## 11. CURRENT METRIC POPULATIONS — IMPORTANT

The current analytics intentionally uses different populations for different metrics.

| View | Trades | Net P&L | Win Rate | Commissions |
|---|---|---|---|---|
| Mix | Open + completed | Completed only | Completed only | Open + completed |
| Weekday | Completed only | Completed only | Completed only | Completed only |
| Symbol | Open + completed | Completed only | Completed only | Open + completed |

This distinction is essential when interpreting numbers.

A Mix or Symbol row may show 20 trades but calculate P&L and Win Rate from only 18 completed trades.

Do not assume that the trade-count denominator equals the population used for every other metric.

Any future changes to these semantics must be deliberate, documented, and tested across all three views.

## 12. COLOUR-CODING SCHEME

Colour coding is tied to the selected metric. It is not a universal assessment of whether the underlying trading activity is good or bad.

The colour means what the selected metric says it means.

### Mix category colours

The current semantic category palette includes:

- CALLS: cyan `#0EA5E9`
- PUTS: violet `#A855F7`
- LONG: emerald `#10B981`
- SHORT: light rose `#FB7185`

The SHORT colour was lightened from the earlier rose-red to improve its appearance.

The Mix category background uses the relevant side/type tint for most metrics.

When Net P&L is selected, the Mix view uses P&L heatmap backgrounds instead of the normal direction/type tint.

### Net P&L colours

Net P&L uses P&L heat-style helpers rather than the ordinary direction/ticker classification tint.

Positive values are represented by green-toned heat colours.

Negative values are represented by red/rose-toned heat colours.

The weekday negative-P&L helper currently includes these branches:

- Stronger negative intensity when the absolute-value ratio is at least `0.25`: background `#6b2434`, border `#b64050`.
- Lower negative intensity: background `#47212c`, border `#86404d`.

The actual positive P&L intensity bands and all helper thresholds are defined in the current source file. Treat `getWeekdayPnlStyle()` and the corresponding heat helpers as the authoritative implementation when revising those colours.

### Win Rate colours

Win Rate colours represent the Win Rate percentage, not the size of the dollar gain or loss.

The current `getWeekdayWinRateStyle()` contains these confirmed bands:

| Win Rate | Background | Border |
|---|---|---|
| 70% and above | `#08745b` | `#0b8b6b` |
| 60% to below 70% | `#0c5b4b` | `#127560` |
| 50% to below 60% | `#103a3b` | `#1b5354` |

The lower bands are defined in the same helper. Consult the actual helper function in `PerformanceBreakdownCard.tsx` before modifying them; do not infer or duplicate unspecified thresholds elsewhere.

A high Win Rate can coexist with negative P&L.

For example, 92% Win Rate can be green while Net P&L is negative if the losses outweigh the profits earned by winning trades.

Similarly, 44% Win Rate can be red even when the total dollar loss is relatively small.

This is not contradictory because Win Rate measures the frequency of winning completed trades, while Net P&L measures the magnitude of the resulting monetary outcomes.

### Trades and commissions heat colours

Trades and Commissions use relative heat-style helpers.

The colour intensity depends on the values used for the corresponding view and its current maximum.

The neutral baseline used by the heat palette includes:

- Background: `#0c1726`
- Border: `#1b2c40`

Other heatmap intensities are defined in the existing source helpers. Do not duplicate or invent independent thresholds for a future change.

### Zero-value neutral styling

Zero-valued cells should not display misleading positive or negative intensity.

The Weekday view now explicitly checks whether the currently selected metric is zero:

- Trades: `row.trades === 0`
- Net P&L: `row.pnl === 0`
- Win Rate: `row.winRate === 0`
- Commissions: `row.commissions === 0`

When the selected metric is zero, Weekday uses:

- Background: `rgba(148, 163, 184, 0.04)`
- Border: `#263548`

This rule applies to the selected metric, not all metrics at once.

For example, a Wednesday with zero Net P&L can still have a non-zero Win Rate. Selecting Net P&L should make its zero value neutral; selecting Win Rate should use the Win Rate styling.

Mix and Symbol already have neutral handling for zero values in the applicable metric styles. Preserve those semantics when changing the colour system.

### Colour-coding rules to preserve

1. Net P&L colours must represent monetary profit/loss.
2. Win Rate colours must represent the win-rate range.
3. Trades and Commissions use their own relative heat calculations.
4. A zero value should use neutral styling where zero-neutral handling is implemented.
5. Category/type colours must not override Net P&L semantics.
6. Do not interpret green Win Rate as proof of profitability.
7. Do not interpret a red Win Rate as proof of a large dollar loss.
8. A colour change must not change the underlying calculation.

## 13. VERIFIED YTD EXAMPLE — STOCKS LONG

A specific YTD example was verified against the converted underlying records.

Diagnostic output for Stocks LONG showed:

- Total trade records: 20
- Completed trade records: 18
- Open trade records: 2
- Completed winning trades: 0
- Completed losses: 18
- Reporting currency: USD
- Completed-trade P&L before display rounding: `-279.42851122489174`
- Displayed Net P&L: `-$279.43`
- Win Rate: `0%`

All 18 completed records in the diagnostic output were classified as `LOSS`.

The two open records had P&L values of `-$0.63` and `-$0.15`, but they were excluded from the completed-trade Net P&L result.

Two completed trades were denominated originally in EUR. Their P&L values were converted through the reporting-currency conversion pipeline before they were summed in the dashboard.

The converted values were therefore not to be added to an unconverted EUR total.

### Verification conclusion

For this particular Stocks LONG YTD dataset:

- The 20-record trade count was correct.
- The 18-record completed-trade count was correct.
- The 0% Win Rate was correct.
- The completed-trade converted P&L total rounded to `-$279.43 USD`, matching the displayed value.

This validates that specific calculation against the underlying diagnostic output. It does not prove that every asset class, symbol, period, account, or FX scenario is correct.

The temporary debugging block added to `app/dashboard/page.tsx` for this verification was subsequently removed. Do not leave the temporary console diagnostics in production code.

## 14. EXISTING SUMMARY CALCULATIONS — SEPARATE FROM THE ROW CALCULATIONS

`generatePerformanceBreakdownAnalytics()` also returns legacy summary fields:

- `longPnL`
- `shortPnL`
- `commissions`
- `netTradingPnL`
- `grossPnL`
- `longTrades`
- `shortTrades`
- `longPercentage`
- `shortPercentage`

The current legacy helpers behave differently from the Mix/Weekday/Symbol row calculations.

### Directional P&L

`calculateLongPnL()` sums `trade.pnl` for all LONG trades without filtering out open records.

`calculateShortPnL()` sums `trade.pnl` for all SHORT trades without filtering out open records.

Therefore, these summary fields can include open-trade P&L.

Do not assume their output must exactly match the completed-only P&L in a Mix row.

### Summary commissions

`calculateCommissions()` sums fees across every trade record, including open records.

### Net and gross summary

The current code calculates:

`netTradingPnL = longPnL + shortPnL`

`grossPnL = netTradingPnL + Math.abs(commissions)`

These legacy summary calculations are separate from the per-row `sumCompletedPnL()` behavior.

The returned summary fields must be reviewed in their own context before changing them. Do not assume that the existence of these fields means they drive all values displayed in the Mix, Weekday, or Symbol views.

## 15. KNOWN DIFFERENCES AND AREAS FOR FUTURE VALIDATION

### A. Different metric populations

Mix and Symbol trade counts include open trades, but Net P&L and Win Rate exclude them.

Weekday counts include completed trades only.

Mix and Symbol commissions include open trades, while Weekday commissions include completed trades only.

These differences are intentional in the current implementation, but future metric changes must preserve or explicitly revise these definitions.

### B. Reporting-currency metadata

The reporting-currency conversion updates `pnl` and `fees` while preserving the original `currency` and `feeCurrency` fields.

Future code must not assume the preserved currency fields describe the converted values.

### C. FX fallback for unsupported currencies

The conversion function returns the original amount if either currency rate is missing.

This can produce incorrect reporting-currency totals when unsupported currencies are encountered.

A future improvement should make missing-rate behavior explicit and testable.

### D. Canonical P&L versus fee aggregation

Performance Breakdown sums the P&L already stored on completed Trade records.

It must not independently subtract fees again without first confirming the canonical P&L definition. Otherwise, commissions may be double-counted.

### E. FIFO and account isolation

Performance Breakdown does not reconstruct trades. It consumes the canonical Trade records passed to it.

Any potential issue involving FIFO matching, multiple accounts, execution pairing, or fee allocation must be investigated in the canonical reconstruction pipeline and tested there.

Do not modify the Performance Breakdown aggregations to compensate for an unverified FIFO issue.

### F. Rounding

The analytics aggregates the numerical P&L values it receives. FX conversion can create fractional-cent values in memory.

Display formatting rounds currency values to two decimal places.

A displayed total may therefore differ slightly from an independently rounded sum of individual values. Verification should compare unrounded internal calculations first, then compare display rounding.

### G. Asset and option classification

Unknown asset types go into Other.

An option contract whose type cannot be recognized unambiguously goes into Opt. Other rather than being guessed to be a CALL or PUT.

Manual options use LONG/SHORT direction rather than the CALL/PUT grouping.

If new broker contract representations are introduced, update classification only after testing the affected contract formats.

## 16. SAFE CHANGE PROCEDURE

Performance Breakdown calculations affect the interpretation of users' trading results.

Follow this process whenever modifying metric or classification logic:

1. Identify the exact incorrect result.
2. Capture the account, date range, reporting currency, and affected records.
3. Determine whether the issue belongs to canonical trades, FX conversion, filtering, aggregation, or display formatting.
4. Define the expected calculation independently.
5. Reproduce the issue using deterministic trade records.
6. Make the smallest relevant change.
7. Run `npm run build`.
8. Verify the affected metric against the underlying trades.
9. Check that the other two views still produce the expected results.
10. Update these master notes when the behavior or assumptions change.

Do not change the canonical trade reconstruction engine merely because a dashboard number appears inconsistent.

Do not change a calculation merely to make colours look more intuitive.

Do not change metric populations without explicitly deciding whether open records should be included.

A calculation change must be tested independently of a colour or formatting change.

## 18. FUTURE DEVELOPMENT PRINCIPLES

Performance Breakdown should remain a thin analytics consumer over canonical trades.

Preserve these principles:

- One canonical trade source.
- One dashboard filtering pipeline.
- One reporting-currency conversion pipeline.
- One Performance Breakdown analytics function.
- Consistent, explicitly defined metric populations.
- No hidden double conversion.
- No duplicate FIFO reconstruction.
- No independent fee deductions in the analytics without verifying the canonical P&L definition.
- No guessing unknown asset or option classifications.
- No colour rules that contradict the selected metric.
- No unverified changes to trading/accounting calculations.

The objective is not just to display trading statistics. It is to make every displayed figure traceable to a clear rule and reproducible from the underlying trade records.
